# Phase 3 Design: Real dispatch lifecycle and tradie opportunity workflow

## Scope and constraint
Phase 3 must extend the existing Phase 1 dispatch model rather than creating a second architecture. The existing migration history already includes the dispatch enum and the `dispatch_offers` table, so the design below keeps that model and adds only the minimum additive schema needed for Phase 3.

This file is the revised design for approval before implementation. It does not modify code yet.

---

## 1. Existing Phase 1 dispatch architecture already in place

### 1.1 Existing database objects
From the Phase 1 migration in `lib/db/migrations/0000_phase1_productionisation.sql`, the base dispatch model already includes:

```sql
CREATE TYPE "dispatch_state" AS ENUM (
  'pending',
  'accepted',
  'declined',
  'expired',
  'cancelled'
);

CREATE TABLE "dispatch_offers" (
  "id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "job_id" integer NOT NULL REFERENCES "jobs"("id") ON DELETE CASCADE,
  "partner_id" integer NOT NULL REFERENCES "partners"("id") ON DELETE CASCADE,
  "state" "dispatch_state" NOT NULL DEFAULT 'pending',
  "offered_at" timestamp with time zone NOT NULL DEFAULT now(),
  "responded_at" timestamp with time zone,
  "created_at" timestamp with time zone NOT NULL DEFAULT now(),
  "updated_at" timestamp with time zone NOT NULL DEFAULT now()
);

CREATE INDEX "dispatch_offers_job_id_idx" ON "dispatch_offers" ("job_id");
CREATE INDEX "dispatch_offers_partner_id_idx" ON "dispatch_offers" ("partner_id");
CREATE INDEX "dispatch_offers_state_idx" ON "dispatch_offers" ("state");
```

This means:
- `dispatch_offers` already exists as the canonical structure for dispatch offers
- `dispatch_state` already exists and is the correct lifecycle model
- `offered_at` and `responded_at` are already in use as event timestamps
- the legacy `created_at`/`updated_at` timestamps are already present

### 1.2 Existing job-state enum and lifecycle
The Phase 1 migration also defines the canonical job lifecycle:

```sql
CREATE TYPE "job_status" AS ENUM (
  'new',
  'reviewing',
  'awaiting_dispatch',
  'dispatching',
  'accepted',
  'in_progress',
  'completed',
  'cancelled'
);
```

The relevant Phase 3 compatibility rule is:
- `awaiting_dispatch -> accepted` is already valid in the canonical model
- Phase 3 must not create a second, competing job lifecycle model
- `declined` and `expired` do not change the job status; they leave the job available for continued dispatch

### 1.3 Existing migration history must be preserved
The migration history is already established:
- `0000_phase1_productionisation.sql` defines the base job/partner/dispatch architecture
- `0001_phase2_auth_rbac.sql` adds the Phase 2 auth/RBAC schema

Phase 3 must use an additive migration only. It must not drop, replace, or rebuild the existing `dispatch_offers` table.

## 2. Phase 3 database delta: additive only

### 2.1 Required additive columns/indexes
Phase 3 requires minimal extension of the existing `dispatch_offers` model to support expiry and safe concurrent constraint enforcement.

Additive migration requirements:

```sql
ALTER TABLE "dispatch_offers"
  ADD COLUMN "expires_at" timestamp with time zone;
```

Then add a partial unique index to enforce one active offer per job:

```sql
CREATE UNIQUE INDEX "dispatch_offers_one_active_per_job_uidx"
ON "dispatch_offers" ("job_id")
WHERE "state" IN ('pending', 'accepted');
```

This is the correct database-level constraint for Phase 3 because:
- it preserves all historical declined/expired/cancelled rows
- it allows multiple historical offers for the same job
- it prevents two active offers from existing at once
- it blocks concurrent creation attempts at the database layer, not just in application code

### 2.2 Why not create a second dispatch-offer table?
Because Phase 1 already established the canonical model. A new table would duplicate state and history and would violate the migration-preservation requirement.

### 2.3 Why this is the minimum safe additive delta
Phase 3 needs only:
- a timeout/expiry value for each offer (`expires_at`)
- a database-enforced uniqueness rule for the active set of offers

No replacement of `dispatch_offers` is required. No destructive migration is allowed.

### 2.4 Drizzle schema extension
The Phase 3 schema extension should be additive in `lib/db/src/schema/index.ts`:

```ts
export const dispatchOffersTable = pgTable(
  "dispatch_offers",
  {
    id: integer("id").generatedByDefaultAsIdentity().primaryKey(),
    jobId: integer("job_id")
      .notNull()
      .references(() => jobsTable.id, { onDelete: "cascade" }),
    partnerId: integer("partner_id")
      .notNull()
      .references(() => partnersTable.id, { onDelete: "cascade" }),
    state: dispatchStateEnum("state").notNull().default("pending"),
    offeredAt: timestamp("offered_at", { withTimezone: true })
      .defaultNow()
      .notNull(),
    respondedAt: timestamp("responded_at", { withTimezone: true }),
    expiresAt: timestamp("expires_at", { withTimezone: true }),
    createdAt: timestamp("created_at", { withTimezone: true })
      .defaultNow()
      .notNull(),
    updatedAt: timestamp("updated_at", { withTimezone: true })
      .defaultNow()
      .notNull(),
  },
  (table) => [
    index("dispatch_offers_job_id_idx").on(table.jobId),
    index("dispatch_offers_partner_id_idx").on(table.partnerId),
    index("dispatch_offers_state_idx").on(table.state),
    uniqueIndex("dispatch_offers_one_active_per_job_uidx")
      .on(table.jobId)
      .where(sql`state IN ('pending', 'accepted')`),
  ],
);
```

This preserves the existing schema while adding the Phase 3 requirement.

## 3. Canonical state models

### 3.1 Canonical job state diagram
The existing Phase 1 enum is the canonical model:

```text
new -> reviewing -> awaiting_dispatch -> dispatching -> accepted -> in_progress -> completed
                                              \                      |
                                               \-> cancelled
```

Phase 3 compatibility rules:
- `awaiting_dispatch -> accepted` is the key dispatch acceptance transition
- a `declined` or `expired` offer does not mutate `jobs.status`; the job remains available for further dispatch
- `dispatching` remains part of the existing enum, but Phase 3 does not need to introduce a separate competing ladder

### 3.2 Canonical dispatch-offer state diagram
The existing `dispatch_state` enum is already the canonical offer lifecycle:

```text
pending -> accepted
   |-> declined
   |-> expired
   |-> cancelled
```

Key Phase 3 rules:
- `pending` is the only state that can be answered by a partner
- `accepted` means the offer was accepted and the job can transition from `awaiting_dispatch` to `accepted`
- `declined` means the offer is closed without changing job availability
- `expired` is an admin/API transition for a timed-out pending offer
- `cancelled` remains a terminal admin cancellation state if needed later

### 3.3 One active offer per job
This is the enforcement model:
- only one `pending` or `accepted` offer may exist per `job_id`
- historical states (`declined`, `expired`, `cancelled`) remain preserved and may coexist for past attempts
- database partial unique index prevents duplicate active offers even under concurrent create attempts
- application-layer validation remains required for user-facing API checks and clearer validation errors

## 4. Existing endpoint retention, changes, and deprecations

### 4.1 Existing endpoints retained unchanged
These remain valid and continue to serve their Phase 1/2 purpose:
- public homeowner job creation endpoint (existing Phase 1/2 API contract)
- public job status token endpoint (existing Phase 2 API contract)
- authenticated admin/partner access middleware and RBAC enforcement

### 4.2 Existing endpoint to be evolved, not duplicated
The existing dispatch decision endpoint is the canonical partner decision API and must be reused.

The Phase 3 design preserves the existing endpoint semantics and evolves it to support:
- explicit validation of offer ownership
- rejection of already-answered offers
- rejection of expired offers
- validation that the requesting partner owns the offer being acted on
- safe visibility of customer data only after acceptance

The endpoint should remain a single decision route rather than creating a competing API family.

### 4.3 Endpoints being deprecated or not introduced
The following are not introduced in Phase 3:
- separate duplicate create-offer endpoints for partner-side dispatching
- separate duplicate offer decision endpoint variants
- any replacement dispatch-offers table or parallel state model
- any visual “dispatch” redesign that duplicates the existing Admin Dispatch Desk without preserving the approved UI

### 4.4 Final API inventory for Phase 3

#### A. Genuinely new endpoints
These are new in Phase 3 and are required for the admin workflow:
1. `POST /api/admin/dispatch-offers` — create an offer for a job to a selected partner
2. `GET /api/admin/jobs-awaiting-dispatch` — list jobs currently waiting for dispatch
3. `GET /api/admin/approved-partners` — list approved partners eligible for dispatch
4. `GET /api/admin/dispatch-offers` — list offer history for admin review
5. `GET /api/partner/offers` — list the current partner's offers
6. `PATCH /api/admin/dispatch-offers/{id}/expire` — manual expiry transition for a pending offer

This is the correct total of six genuinely new endpoints.

#### B. Existing endpoints modified for Phase 3
1. existing partner decision endpoint for accepting/declining an offer, evolved to enforce:
   - correct partner ownership
   - state validation (`pending` only)
   - expired rejection
   - no duplicate decisions
   - conditional data exposure based on offer state

#### C. Existing endpoints retained unchanged
1. homeowner job creation endpoint
2. homeowner public job status endpoint using the job status token
3. existing admin and partner auth routes and RBAC middleware

## 5. Security and data exposure rules

### 5.1 Pre-acceptance partner data exposure
Before acceptance, a partner response must not expose any identifying customer details.

Specifically, the offer payload returned to a partner before acceptance must never include:
- customer name
- customer phone
- customer email
- exact street address, if stored in the job record
- any other unnecessary identifying information

Allowed pre-acceptance fields are limited to:
- job reference
- trade
- suburb
- postcode
- urgency
- preferred time
- summary/description
- timing metadata

### 5.2 Post-acceptance data exposure
Once the offer is accepted, the partner may receive only what is required to complete the service:
- customer name
- customer phone
- customer email
- service address (if required for job completion)
- job details necessary to perform the work

This should still remain minimal and appropriate to the job, not a broad dump of all customer data.

### 5.3 Admin access
Admin users may continue to access customer information through authenticated admin job endpoints and admin offer history views as needed for operational control.

However, the `dispatch_offers` list responses themselves should remain appropriately scoped and should not expose customer private data in the offer list payloads unless a specific admin endpoint explicitly requires it.

### 5.4 Public customer status page
The public status page must remain a customer-only view using the status token flow. It must reflect the job lifecycle without exposing internal partner/admin dispatch data.

The customer should see:
- current job status
- the latest lifecycle state (for example, `awaiting_dispatch`, `accepted`, `in_progress`)
- public job metadata

It must not expose:
- partner identity before acceptance
- internal offer history
- internal admin-only metadata

## 6. Phase 3 implementation rules

### 6.1 Rule: one active offer per job
The database unique index is the enforcement mechanism:

```sql
CREATE UNIQUE INDEX "dispatch_offers_one_active_per_job_uidx"
ON "dispatch_offers" ("job_id")
WHERE "state" IN ('pending', 'accepted');
```

This ensures:
- only one active offer at a time
- historical declined/expired/cancelled records remain preserved
- a job cannot accumulate multiple open offers concurrently

### 6.2 Rule: duplicate or invalid decisions are rejected
The decision endpoint must enforce:
- `state = 'pending'` only
- `responded_at IS NULL` only
- partner ownership must match the offer's `partner_id`
- `expires_at` must not be past-due
- `decision` must be one of `accepted` or `declined`

If any of these fail, return a 4xx response and do not mutate the job state.

### 6.3 Rule: accept path transitions the job correctly
When a partner accepts an offer:
- `dispatch_offers.state` changes from `pending` to `accepted`
- `dispatch_offers.responded_at` is set to the timestamp of the decision
- the job status transitions from `awaiting_dispatch` to `accepted`
- if later the job proceeds, the existing job model may advance to `in_progress` using the current lifecycle rules

### 6.4 Rule: decline path keeps the job dispatchable
When a partner declines an offer:
- `dispatch_offers.state` changes from `pending` to `declined`
- `dispatch_offers.responded_at` is set
- the job remains available for further dispatch (status stays `awaiting_dispatch` unless another workflow changes it)

### 6.5 Rule: expiry path is manual/API-only in Phase 3
No background scheduler is part of this phase.

The expiry flow is explicitly:
- admin or API-triggered transition from `pending` to `expired`
- no automated worker required
- the job remains dispatchable afterward

## 7. Frontend impact and UX expectations

### 7.1 No separate visual redesign
Phase 3 should not create a separate `/admin/dispatch` visual redesign unless the current admin flow genuinely cannot support the required functionality. The preferred pattern is to enhance the existing approved admin Dispatch Desk experience rather than build duplicate views.

The UI should preserve the current SourceTradie design language and approved layout.

### 7.2 Admin experience
The admin experience should allow:
- viewing jobs in `awaiting_dispatch`
- viewing approved partners
- creating an offer for a selected partner and job
- seeing active vs historical offer state
- preventing duplicate active offers
- viewing past offer history

### 7.3 Partner dashboard experience
The partner dashboard should be updated with real offer data instead of hardcoded cards.

It must show:
- safe job preview metadata
- action buttons for accept/decline
- safe visibility rules before acceptance
- full job/customer details only after acceptance

---

## 8. Final approval summary
This revised Phase 3 design is intentionally additive and compatible with the existing schema, migration history, and lifecycle model.

The design preserves:
- the existing `dispatch_offers` table
- the existing `dispatch_state` enum
- the existing `job_status` enum and `awaiting_dispatch -> accepted` transition
- the current migration sequence and data integrity

It adds only the minimal missing pieces needed for Phase 3:
- `expires_at` on the existing offer record
- a partial unique index enforcing one active offer per job
- explicit admin and partner offer workflows built on the existing dispatch model

This is the correct baseline for implementation approval.
